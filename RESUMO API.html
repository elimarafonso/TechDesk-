Revisão rápida: camadas de uma API REST em Spring Boot

Teoria curta + código comentado para cada camada da aplicação. Use a busca para filtrar por anotação ou palavra-chave, ou navegue pelo menu lateral. Pensado para consulta rápida, não para ser lido de uma vez.

Base de versões (ago/2026): Java 17+ · Spring Boot 3.5.x (LTS) ou 4.0/4.1.x (linha atual) — as anotações e o código desta página valem para as duas. Números de versão de dependências (springdoc, jjwt, Flyway...) mudam com frequência: trate os exemplos abaixo como ponto de partida e confira sempre a versão mais recente no Maven Central antes de fixar no seu pom.xml.
Controller

Camada de entrada HTTP

Recebe a requisição, delega ao Service e devolve a resposta. Não deve conter regra de negócio nem acesso direto ao banco.

Anotação base da classe

@RestController = @Controller + @ResponseBody (retorno já vira JSON). @RequestMapping define o prefixo comum de URL.

@RestController
@RequestMapping("/api/produtos") // prefixo de todos os endpoints
public class ProdutoController {
    private final ProdutoService service; // injeção via construtor
}

GET com parâmetro de caminho

@PathVariable captura um trecho da URL (ex: o id do recurso).

@GetMapping("/{id}")
public ResponseEntity<ProdutoDTO> buscar(@PathVariable Long id) {
    return ResponseEntity.ok(service.buscarPorId(id));
}

GET com parâmetro de query (opcional)

@RequestParam captura valores de query string. "required = false" torna o filtro opcional.

@GetMapping
public List<ProdutoDTO> listar(
        @RequestParam(required = false) String nome) {
    return nome == null ? service.listarTodos() : service.buscarPorNome(nome);
}

POST com corpo validado

@RequestBody converte o JSON recebido em objeto Java. @Valid ativa as validações do DTO.

@PostMapping
public ResponseEntity<ProdutoDTO> criar(@Valid @RequestBody ProdutoRequestDTO dto) {
    ProdutoDTO criado = service.criar(dto);
    return ResponseEntity.status(HttpStatus.CREATED).body(criado); // 201
}

PUT (atualização completa)

Recebe id pela URL e o novo estado completo do recurso no corpo.

@PutMapping("/{id}")
public ResponseEntity<ProdutoDTO> atualizar(
        @PathVariable Long id, @Valid @RequestBody ProdutoRequestDTO dto) {
    return ResponseEntity.ok(service.atualizar(id, dto));
}

DELETE

Ao remover com sucesso, o padrão é responder 204 No Content (sem corpo).

@DeleteMapping("/{id}")
public ResponseEntity<Void> deletar(@PathVariable Long id) {
    service.deletar(id);
    return ResponseEntity.noContent().build(); // 204
}

Paginação com Pageable

O Spring extrai automaticamente page, size e sort da query string.

@GetMapping("/paginado")
public Page<ProdutoDTO> listarPaginado(
        @PageableDefault(size = 20, sort = "nome") Pageable pageable) {
    return service.listarPaginado(pageable);
}
// chamada: GET /api/produtos/paginado?page=0&size=20&sort=preco,desc

ResponseEntity com status customizado

Dá controle total sobre status code, headers e corpo da resposta.

return ResponseEntity
        .status(HttpStatus.CONFLICT)   // 409
        .header("X-Motivo", "duplicado")
        .body(erroDTO);
  • Controller "magro": nada de lógica de negócio aqui — apenas orquestra a chamada ao Service.
  • URLs com substantivo no plural (/produtos), nunca verbos (/criarProduto ❌).
  • Sempre devolva o status HTTP correto (201 ao criar, 204 ao deletar, 404 quando não encontrado).
  • Versione a API quando fizer mudanças que quebram compatibilidade: /api/v1/produtos.
  • Nunca retorne a Entity diretamente — sempre um DTO.
Entity

Mapeamento objeto-relacional (JPA)

Classe Java que representa uma tabela do banco. Cada instância = uma linha.

Estrutura mínima

@Entity marca a classe; @Id define a chave primária; @GeneratedValue configura o auto-incremento.

@Entity
@Table(name = "produtos")
public class Produto {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 120)
    private String nome;
}

Relacionamento N:1 (@ManyToOne)

Vários produtos pertencem a uma categoria. FetchType.LAZY evita carregar a categoria sem necessidade.

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(name = "categoria_id")
private Categoria categoria;

Relacionamento 1:N (@OneToMany)

"mappedBy" indica qual atributo do outro lado é o "dono" do relacionamento (evita tabela extra).

@OneToMany(mappedBy = "categoria", cascade = CascadeType.ALL, orphanRemoval = true)
private List<Produto> produtos = new ArrayList<>();

Relacionamento N:N (@ManyToMany)

Usa uma tabela intermediária, definida via @JoinTable.

@ManyToMany
@JoinTable(name = "produto_tag",
    joinColumns = @JoinColumn(name = "produto_id"),
    inverseJoinColumns = @JoinColumn(name = "tag_id"))
private Set<Tag> tags = new HashSet<>();

Enum mapeado

EnumType.STRING grava o nome do enum (legível no banco); evite EnumType.ORDINAL (grava a posição, frágil).

@Enumerated(EnumType.STRING)
@Column(nullable = false)
private StatusPedido status; // ex: ABERTO, PAGO, CANCELADO

Callbacks de ciclo de vida

Métodos executados automaticamente antes de inserir/atualizar o registro.

@PrePersist
public void aoCriar() { this.criadoEm = LocalDateTime.now(); }

@PreUpdate
public void aoAtualizar() { this.atualizadoEm = LocalDateTime.now(); }
  • Nunca exponha a Entity direto na API — use sempre um DTO (evita acoplamento e vazamento de dados).
  • Prefira FetchType.LAZY por padrão; use EAGER só quando necessário.
  • Cuidado com equals()/hashCode() em Entities com relacionamentos — prefira basear só no id.
  • Use BigDecimal para valores monetários, nunca double/float.
  • Em produção, gerencie o schema com Flyway/Liquibase — nunca ddl-auto=update.
Repository

Acesso a dados (Spring Data JPA)

Interfaces que o Spring implementa automaticamente. Sem SQL manual na maioria dos casos.

Interface base

Herdar de JpaRepository já traz save, findById, findAll, deleteById, count, etc.

public interface ProdutoRepository extends JpaRepository<Produto, Long> {
    //                                        ^ Entity        ^ tipo do id
}

Query methods (nome do método vira SQL)

O Spring interpreta o nome do método e gera a consulta automaticamente.

List<Produto> findByNomeContainingIgnoreCase(String nome); // LIKE %nome%
List<Produto> findByPrecoLessThanEqual(BigDecimal preco);   // preco <= ?
boolean existsByNome(String nome);
long countByQuantidadeEstoque(Integer quantidade);
List<Produto> findTop5ByOrderByPrecoDesc();

Consulta customizada com @Query (JPQL)

Use quando o nome do método ficaria complexo demais.

@Query("SELECT p FROM Produto p WHERE p.preco BETWEEN :min AND :max")
List<Produto> buscarPorFaixaDePreco(@Param("min") BigDecimal min,
                                     @Param("max") BigDecimal max);

Consulta SQL nativa

Para casos que a JPQL não cobre bem (funções específicas do banco).

@Query(value = "SELECT * FROM produtos WHERE estoque = 0", nativeQuery = true)
List<Produto> buscarSemEstoque();

UPDATE/DELETE customizado

@Modifying é obrigatório em queries de alteração; precisa rodar dentro de uma transação.

@Modifying
@Transactional
@Query("UPDATE Produto p SET p.quantidadeEstoque = 0 WHERE p.id = :id")
void zerarEstoque(@Param("id") Long id);

Paginação nativa

Basta trocar o retorno para Page<T> e receber um Pageable — já vem pronto no JpaRepository.

Page<Produto> findByNomeContainingIgnoreCase(String nome, Pageable pageable);
  • Repository deve ser "burro": só consulta dados, nunca contém regra de negócio.
  • Prefira query methods para casos simples; @Query para casos complexos.
  • Use projeções (interfaces ou DTOs) quando não precisar da Entity inteira — melhora performance.
  • Sempre pagine listagens que podem crescer muito.
Service

Regras de negócio

Orquestra chamadas ao Repository e aplica as regras da aplicação. Não conhece HTTP.

Injeção de dependência via construtor

@RequiredArgsConstructor (Lombok) gera o construtor para todo atributo "final" — forma recomendada de injeção.

@Service
@RequiredArgsConstructor
public class ProdutoService {
    private final ProdutoRepository repository; // nunca @Autowired em campo
}

Transação de escrita

@Transactional garante que a operação seja atômica (tudo ou nada).

@Transactional
public ProdutoDTO criar(ProdutoRequestDTO dto) {
    Produto salvo = repository.save(toEntity(dto));
    return ProdutoDTO.fromEntity(salvo);
}

Transação de leitura (otimizada)

readOnly = true evita overhead de controle de transação em consultas.

@Transactional(readOnly = true)
public List<ProdutoDTO> listarTodos() {
    return repository.findAll().stream().map(ProdutoDTO::fromEntity).toList();
}

Buscar ou lançar exceção de negócio

Padrão comum: buscar por id e, se não existir, lançar uma exceção customizada (tratada globalmente).

private Produto buscarOuFalhar(Long id) {
    return repository.findById(id)
            .orElseThrow(() -> new ProdutoNaoEncontradoException(id));
}
  • Toda regra de negócio mora aqui — não no Controller nem no Repository.
  • Service não deve conhecer detalhes HTTP (nada de HttpServletRequest, ResponseEntity aqui).
  • Um Service pode ser reaproveitado por múltiplos Controllers (REST, mensageria, jobs...).
  • Métodos pequenos e com um propósito único facilitam testes unitários com mocks.
DTO

Data Transfer Object

Desacopla o contrato da API (o que trafega) do modelo interno do banco.

DTO de requisição (record)

Records são imutáveis e enxutos — ideais para DTOs. Nunca inclua "id" nem campos controlados pelo servidor.

public record ProdutoRequestDTO(
        @NotBlank String nome,
        @NotNull @PositiveOrZero BigDecimal preco) {}

DTO de resposta + mapeamento

Centralizar a conversão Entity → DTO em um método de fábrica evita duplicação.

public record ProdutoDTO(Long id, String nome, BigDecimal preco) {
    public static ProdutoDTO fromEntity(Produto p) {
        return new ProdutoDTO(p.getId(), p.getNome(), p.getPreco());
    }
}

DTO → Entity (na criação)

Converte o dado recebido em Entity antes de persistir.

private Produto toEntity(ProdutoRequestDTO dto) {
    return Produto.builder().nome(dto.nome()).preco(dto.preco()).build();
}
  • Nunca use a Entity como corpo de request/response — sempre um DTO dedicado.
  • DTOs de entrada e saída podem (e costumam) ser diferentes.
  • Prefira record a classes tradicionais: menos código, imutabilidade de graça.
  • Em projetos maiores, considere MapStruct para gerar o mapeamento automaticamente.
Validação

Bean Validation

Valida os dados de entrada antes de qualquer regra de negócio rodar.

Anotações mais usadas

Aplicadas diretamente nos campos do DTO.

@NotNull            // não pode ser null
@NotBlank           // string: não pode ser null, vazia ou só espaços
@Size(min=3,max=50) // tamanho mínimo/máximo
@Email              // formato de e-mail válido
@Positive           // número > 0
@Past / @Future     // data no passado/futuro

Ativando a validação no Controller

Sem @Valid, as anotações do DTO são ignoradas.

@PostMapping
public ResponseEntity<ProdutoDTO> criar(@Valid @RequestBody ProdutoRequestDTO dto) { ... }

Validando @PathVariable / @RequestParam

Precisa de @Validated na classe do Controller (não apenas @Valid).

@RestController
@Validated
public class ProdutoController {
    @GetMapping("/{id}")
    public ProdutoDTO buscar(@PathVariable @Positive Long id) { ... }
}
  • Sempre valide dados vindos de fora (corpo, query params, headers) — nunca confie no cliente.
  • Use mensagens customizadas e claras: @NotBlank(message = "nome é obrigatório").
  • Combine validação de formato (Bean Validation) com validação de negócio (no Service).
Exceções

Tratamento global de erros

Centraliza o tratamento de erros em vez de duplicar try/catch em cada Controller.

Exceção de negócio customizada

public class ProdutoNaoEncontradoException extends RuntimeException {
    public ProdutoNaoEncontradoException(Long id) {
        super("Produto não encontrado: " + id);
    }
}

Handler global

@RestControllerAdvice intercepta exceções de todos os Controllers da aplicação.

@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(ProdutoNaoEncontradoException.class)
    public ResponseEntity<ErroDTO> tratar(ProdutoNaoEncontradoException ex) {
        return ResponseEntity.status(404).body(new ErroDTO(ex.getMessage()));
    }
}

Tratando erros de validação (@Valid)

@ExceptionHandler(MethodArgumentNotValidException.class)
public ResponseEntity<ErroDTO> tratarValidacao(MethodArgumentNotValidException ex) {
    String msg = ex.getBindingResult().getFieldError().getDefaultMessage();
    return ResponseEntity.badRequest().body(new ErroDTO(msg)); // 400
}

Atalho rápido: ResponseStatusException

Útil para casos pontuais, sem precisar criar uma classe de exceção nova.

throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Produto não encontrado");

Padrão atual: ProblemDetail (RFC 9457)

Desde o Spring Framework 6 / Spring Boot 3, existe um formato de erro padronizado embutido — hoje é a abordagem recomendada em vez de criar seu próprio ErroDTO do zero.

# habilita o formato padrão em toda a aplicação
spring.mvc.problemdetails.enabled=true
@ExceptionHandler(ProdutoNaoEncontradoException.class)
public ProblemDetail tratar(ProdutoNaoEncontradoException ex) {
    ProblemDetail problema = ProblemDetail.forStatusAndDetail(
            HttpStatus.NOT_FOUND, ex.getMessage());
    problema.setTitle("Produto não encontrado");
    return problema; // Content-Type: application/problem+json
}
  • Nunca deixe stack trace vazar para o cliente — sempre uma resposta JSON padronizada.
  • Tenha um handler "genérico" (Exception.class) como rede de segurança, devolvendo 500.
  • Em projetos novos, prefira ProblemDetail (padrão RFC 9457, já embutido) a um DTO de erro próprio — só crie um formato customizado se o time tiver um motivo específico.
Configuração

application.properties & profiles

Centraliza configurações da aplicação, separadas por ambiente.

Configurações essenciais

server.port=8080
spring.datasource.url=jdbc:postgresql://localhost:5432/meudb
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.show-sql=true

Profiles (dev, prod...)

Arquivos application-{profile}.properties sobrescrevem o padrão conforme o profile ativo.

# application-dev.properties
spring.jpa.hibernate.ddl-auto=update

# ativar via linha de comando:
# java -jar app.jar --spring.profiles.active=dev

Lendo configurações customizadas

@Value("${app.nome-empresa}")
private String nomeEmpresa;

// ou agrupando várias propriedades:
@ConfigurationProperties(prefix = "app")
public record AppProperties(String nomeEmpresa, int limitePagina) {}
  • Segredos (senha de banco, chave JWT) sempre via variável de ambiente, nunca no código.
  • ddl-auto=update só em desenvolvimento — em produção use Flyway/Liquibase.
  • Um profile por ambiente (dev, test, prod) evita configuração condicional espalhada no código.
Migrations

Versionamento de schema (Flyway)

Controla e versiona as alterações da estrutura do banco, em vez de deixar o Hibernate criar/alterar tabelas sozinho.

Dependência

Basta adicionar ao pom.xml — o Flyway roda automaticamente no startup da aplicação.

<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>

Estrutura de arquivos

Cada arquivo representa uma versão do schema; o Flyway aplica em ordem e nunca re-executa o que já rodou.

src/main/resources/db/migration/
├── V1__criar_tabela_produtos.sql
├── V2__adicionar_coluna_estoque.sql
└── V3__criar_tabela_categorias.sql

Exemplo de migration

-- V1__criar_tabela_produtos.sql
CREATE TABLE produtos (
    id BIGSERIAL PRIMARY KEY,
    nome VARCHAR(120) NOT NULL,
    preco NUMERIC(10,2) NOT NULL
);

Configuração

Com o Flyway ativo, o Hibernate só valida se o schema bate com as Entities — nunca cria ou altera tabelas sozinho.

spring.flyway.enabled=true
spring.jpa.hibernate.ddl-auto=validate
  • Nunca edite uma migration já aplicada em produção — crie sempre uma nova.
  • Nomeie os arquivos em ordem crescente: V1, V2, V3... o Flyway depende dessa numeração.
  • Rode as migrations automaticamente no startup — evita passos manuais de deploy.
Segurança

Spring Security & JWT

Autenticação (quem é o usuário) e autorização (o que ele pode fazer).

Cadeia de segurança básica

@Bean
public SecurityFilterChain filterChain(HttpSecurity http) throws Exception {
    http.csrf(c -> c.disable())
        .sessionManagement(s -> s.sessionCreationPolicy(SessionCreationPolicy.STATELESS))
        .authorizeHttpRequests(auth -> auth
            .requestMatchers("/api/auth/**").permitAll()
            .anyRequest().authenticated());
    return http.build();
}

Codificação de senha

Nunca armazene senha em texto puro — sempre com hash (BCrypt é o padrão de mercado).

@Bean
public PasswordEncoder passwordEncoder() { return new BCryptPasswordEncoder(); }

Restringindo por papel (role)

Desde o Spring Security 6, @PreAuthorize só funciona com @EnableMethodSecurity habilitado — antes disso, era @EnableGlobalMethodSecurity (anotação antiga, evite em projetos novos).

@Configuration
@EnableMethodSecurity // habilita @PreAuthorize/@PostAuthorize na aplicação
public class MethodSecurityConfig { }
@PreAuthorize("hasRole('ADMIN')")
@DeleteMapping("/{id}")
public void deletar(@PathVariable Long id) { ... }

Fluxo JWT (resumo)

O cliente faz login uma vez e reutiliza o token — nenhuma sessão fica guardada no servidor.

1. POST /api/auth/login (email + senha) → servidor gera um JWT
2. Cliente guarda o token e envia em cada chamada:
   Authorization: Bearer <token>
3. Um filtro (OncePerRequestFilter) valida o token a cada requisição
  • APIs REST devem ser stateless: nada de sessão em memória no servidor.
  • Tokens JWT devem ter tempo de expiração curto.
  • Chave de assinatura do JWT nunca deve ir para o repositório de código.
CORS

Cross-Origin Resource Sharing

Necessário quando o front-end roda em outro domínio/porta da API (ex: React em localhost:3000 chamando a API em localhost:8080).

Configuração global

Libera as origens permitidas para toda a aplicação, em um único lugar.

@Bean
public WebMvcConfigurer corsConfigurer() {
    return new WebMvcConfigurer() {
        public void addCorsMappings(CorsRegistry registry) {
            registry.addMapping("/api/**")
                    .allowedOrigins("http://localhost:3000")
                    .allowedMethods("GET","POST","PUT","DELETE");
        }
    };
}

CORS em um único Controller

Útil para liberar apenas um recurso específico, sem afetar o restante da API.

@CrossOrigin(origins = "http://localhost:3000")
@RestController
@RequestMapping("/api/produtos")
public class ProdutoController { ... }

CORS junto com Spring Security

Com o Spring Security ativo, é preciso habilitar o CORS também na cadeia de segurança.

http.cors(Customizer.withDefaults())
    .csrf(c -> c.disable());
  • Nunca use allowedOrigins("*") em produção junto com credenciais habilitadas.
  • Libere apenas os domínios reais do front-end (dev, staging, produção) — nunca um curinga solto.
  • CORS é aplicado pelo navegador: não substitui autenticação/autorização no servidor.
Testes

Testes automatizados

Garantem que o comportamento esperado continue funcionando conforme o código muda.

Teste unitário do Service (Mockito)

Não sobe o contexto do Spring nem o banco — só testa a lógica isolada, usando dublês (mocks).

@ExtendWith(MockitoExtension.class)
class ProdutoServiceTest {
    @Mock ProdutoRepository repository;
    @InjectMocks ProdutoService service;

    @Test
    void deveLancarExcecaoSeNaoEncontrar() {
        when(repository.findById(1L)).thenReturn(Optional.empty());
        assertThrows(ProdutoNaoEncontradoException.class, () -> service.buscarPorId(1L));
    }
}

Teste da camada web (@WebMvcTest)

Sobe só o Controller; o Service é substituído por um mock.

@WebMvcTest(ProdutoController.class)
class ProdutoControllerTest {
    @Autowired MockMvc mockMvc;
    @MockBean ProdutoService service;

    @Test
    void deveRetornar404() throws Exception {
        mockMvc.perform(get("/api/produtos/99")).andExpect(status().isNotFound());
    }
}

Teste de integração completo

Sobe a aplicação inteira (contexto Spring + banco), simulando um cenário real de ponta a ponta.

@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)
class ProdutoApiIT {
    @Autowired TestRestTemplate rest;

    @Test
    void deveCriarProduto() {
        var resp = rest.postForEntity("/api/produtos", novoProdutoDTO, Object.class);
        assertThat(resp.getStatusCode()).isEqualTo(HttpStatus.CREATED);
    }
}
  • Teste regras de negócio, não getters/setters gerados pelo Lombok.
  • Prefira muitos testes unitários rápidos (Service) a poucos testes de integração lentos.
  • Nomeie o teste pelo comportamento esperado: deveRetornar404QuandoProdutoNaoExiste.
Documentação

Swagger / OpenAPI

Gera uma documentação interativa da API automaticamente, a partir do próprio código.

Dependência

Só de adicionar essa dependência, o Swagger UI já fica disponível — sem configuração extra. A versão muda com frequência: springdoc-openapi série 2.x acompanha Spring Boot 3.5.x, série 3.x acompanha Spring Boot 4.x — confira a última tag em springdoc.org antes de fixar.

<dependency>
    <groupId>org.springdoc</groupId>
    <artifactId>springdoc-openapi-starter-webmvc-ui</artifactId>
    <version><!-- use a última da série 2.x (Boot 3.5) ou 3.x (Boot 4) --></version>
</dependency>

Personalizando título e versão

@Bean
public OpenAPI apiInfo() {
    return new OpenAPI().info(new Info()
            .title("Catálogo API")
            .version("v1"));
}

Documentando um endpoint específico

Anotações opcionais para enriquecer a documentação gerada automaticamente.

@Operation(summary = "Busca um produto pelo id")
@ApiResponse(responseCode = "404", description = "Produto não encontrado")
@GetMapping("/{id}")
public ProdutoDTO buscar(@PathVariable Long id) { ... }

Acessando a documentação

Swagger UI (interface interativa): /swagger-ui.html
JSON da especificação OpenAPI:      /v3/api-docs
  • A documentação é gerada a partir do código — mantê-lo claro já mantém a doc atualizada.
  • Use @Operation e @ApiResponse nos endpoints mais importantes ou não óbvios.
  • Compartilhe a URL do Swagger UI com front-end/mobile/QA como "contrato vivo" da API.
Docker

Empacotamento e deploy

Empacota a aplicação com tudo que ela precisa para rodar da mesma forma em qualquer ambiente.

Gerar o .jar executável

./mvnw clean package -DskipTests

Dockerfile (multi-stage build)

O estágio final não carrega Maven nem código-fonte — só o .jar, gerando uma imagem menor e mais segura.

FROM maven:3.9-eclipse-temurin-17 AS build
WORKDIR /app
COPY . .
RUN mvn clean package -DskipTests

FROM eclipse-temurin:17-jre-alpine
COPY --from=build /app/target/*.jar app.jar
EXPOSE 8080
ENTRYPOINT ["java","-jar","app.jar"]

Build e execução

docker build -t minha-api .
docker run -p 8080:8080 minha-api

Configurando por variável de ambiente

Variáveis de ambiente sobrescrevem automaticamente as propriedades equivalentes do application.properties.

docker run -p 8080:8080 \
  -e SPRING_DATASOURCE_URL=jdbc:postgresql://host:5432/db \
  -e SPRING_PROFILES_ACTIVE=prod \
  minha-api
  • Use multi-stage build: a imagem final não deve conter Maven nem código-fonte.
  • Nunca coloque senhas/segredos direto no Dockerfile — use variáveis de ambiente.
  • Configure um profile de produção (spring.profiles.active=prod) separado do de desenvolvimento.

Códigos de status HTTP

Guia rápido de qual status devolver em cada situação.

CódigoNomeQuando usar
200OKSucesso em GET, PUT, PATCH
201CreatedRecurso criado com sucesso (POST)
204No ContentSucesso sem corpo de resposta (DELETE)

Boas práticas gerais de API REST

  • URLs com substantivo no plural e sem verbos: /pedidos, nunca /buscarPedidos.
  • O verbo HTTP expressa a ação (GET, POST, PUT, PATCH, DELETE) — a URL representa apenas o recurso.
  • GET, PUT e DELETE devem ser idempotentes (repetir a chamada produz o mesmo resultado final).
  • Sempre pagine listagens que podem crescer (?page=0&size=20).
  • Versione a API (/api/v1/...) antes de introduzir mudanças que quebram contrato.
  • Documente com Swagger/OpenAPI — endpoint /swagger-ui.html gerado automaticamente.
  • Libere CORS explicitamente apenas para as origens confiáveis do front-end.
  • Camadas bem separadas (Controller → Service → Repository) facilitam manutenção e testes.
  • Nunca exponha stack trace, senha ou dados sensíveis nas respostas de erro.
